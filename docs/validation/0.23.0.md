- Minecraft 1.21.1 / NeoForge 21.1.216 / JDK 21；主战斗协议 **`8`**（`TacticalNetwork.PROTOCOL`），独立技能协议 **`3`**（`SkillNetwork.PROTOCOL`）；0.22.2 为 `6` / `1`，两者不混连。

- 当前候选范围：**多人合作 PvE，多场并行已实现未完整验收**。不同维度各自开战；同一维度内战区包围盒重叠按**保守 AABB 拒绝**新场（宁可拒绝一次可恢复的开战，也不让两场重叠）。加入有两条：显式邀请，以及附近战场直接确认加入；服务端都按连接身份重算距离、维度、资格、容量与安全动作边界，不要求「必须管理员邀请」。默认单场上限 `maxBattlePlayers` 4（`1..16`，每场构造时快照，可配置不等于已验证承载）。
- 明确**不含**：PvP、玩家阵营持久化、跨维度同场战斗（不同维度各自开战属于多场并行）、外部观众、断线后自动恢复参战身份。长期计划与预留边界见 [长期路线图](../ROADMAP.md)。

## 服务端生命周期 epoch 轮换（源码修复 + 确定性测试，**尚未编译验证**）

修复（[MembershipGenerations.java](../../neoforge-1.21.1/src/main/java/com/tactical/neoforge/battle/multi/MembershipGenerations.java)）：

- `EPOCH` 改为 `volatile` 并在**停服接缝** `onServerStopped()` 中轮换为新值（与旧值比较，保证不同），同时清 `CURRENT`/`TOP`；`ServerStoppedEvent` 处理路径改调该接缝（[BattleDiscovery.java](../../neoforge-1.21.1/src/main/java/com/tactical/neoforge/battle/BattleDiscovery.java)）。

## 客户端 payload 连接 guard（源码 + 单元测试，**尚未编译验证**）

背景：NeoForge 21.1.216 的 `IPayloadContext.connection()` 绑定到收包时的那个 listener，`enqueueWork` 只把任务排进主线程、执行时**不再复核**；旧连接排队的任务是否可能在切换连接后执行，源码层面无法排除。因此按批准的跨场/重连同步保护，在**每个 clientbound payload 的唯一主线程应用点**加连接 guard（[ClientPayloadGate.java](../../neoforge-1.21.1/src/main/java/com/tactical/neoforge/client/ClientPayloadGate.java)），判断在**排队任务执行时**进行，且**不读 `context.player()`**（它解析的是执行时刻的全局 player）：

1. 客户端当前有连接（`Minecraft.getInstance().getConnection()` 非 null）；
2. 该 listener 仍在 `isAcceptingMessages()`；
3. 该 listener 持有的 `Connection` 对象与收包时捕获的 `context.connection()` **同一实例**。

三条任一不满足即丢弃（fail-closed）。已覆盖的实际客户端入口（全部 10 个 clientbound 注册）：`BattleStatePacket`（state）、`BattleLogPacket`（log）、`AttackRangeSnapshotPacket`、`CreeperTelegraphPacket`、`SkillStatePacket`、`SkillPreviewResponsePacket`、`PlayerStepPacket`、`MoveChoiceOfferPacket`、`NearbyBattlesPacket`、`JoinBattleResultPacket`；既有 membership/session 验证（服务端代次、epoch、会话身份）保持原样叠加，不替代。实现放在 `client` 包且只被 handler lambda 引用，注册阶段不触发客户端类加载。

单元测试（[ClientPayloadGateTest.java](../../neoforge-1.21.1/src/test/java/com/tactical/neoforge/client/ClientPayloadGateTest.java)，身份源可注入，无需真实客户端）：旧任务先排队 → 连接切换 → 旧任务执行被拒、新连接首包接受；同服同 epoch 的新连接首包接受而旧对象被拒；同一连接上重生继续接受；无当前连接 fail-closed；listener 已停止接受时同对象也被拒；`arrived` 为 null 一律不应用。

**边界与未决**：`Minecraft.getConnection()` 依赖已安装的 player。按安装版源码的**正常登录顺序**，预期 player 先安装、之后才处理 play 阶段的 payload，但**真实首包时序未验证**；本 guard 丢弃的包**没有 ack、也没有无条件重发保证**——入场与状态变化可能产生后续快照，但不能据此认定能补回被丢弃的首包。本条**不是**已复现的真实网络问题，只是静态复核确认的状态机反例与据此加的防线；登录/首包实测留待用户恢复桌面后执行。

**状态：已编译并通过单元测试**（见下文"修复后的标准构建与测试"：`ClientPayloadGateTest` 6 例随 243 项一起执行，0 失败）。真实客户端的登录/首包时序仍**未验证**（无安全显示途径），本 guard 在真实网络中的行为不作通过结论。
